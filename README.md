# Service Booking & Review API

[![CI](https://github.com/ManojGowda2006/Bodhrik_FullStack_Assessment/actions/workflows/ci.yml/badge.svg)](https://github.com/ManojGowda2006/Bodhrik_FullStack_Assessment/actions/workflows/ci.yml)

A Django REST API for a service booking platform: providers offer time slots, customers book them, and completed bookings can be reviewed. Review summaries are generated by a background worker through a Redis queue.

The design reasoning (schema, RBAC, production gaps) is in **[NOTE.md](NOTE.md)**.

## Stack

| Layer | Choice |
|---|---|
| API | Django 5.2 + Django REST Framework |
| Auth | JWT (djangorestframework-simplejwt) |
| Database | PostgreSQL 16 |
| Queue + cache | Redis 7 with django-rq (queue) and Django's Redis cache backend |
| Runtime | Docker Compose: `web` (gunicorn), `worker` (rqworker), `db`, `redis` |
| Quality | pytest, ruff, GitHub Actions (lint, tests, smoke test) |

## Run it

Requirements: Docker with the Compose plugin.

```bash
git clone https://github.com/ManojGowda2006/Bodhrik_FullStack_Assessment.git
cd Bodhrik_FullStack_Assessment
cp .env.example .env            # set DJANGO_SECRET_KEY to any long random string
docker compose up -d --build --wait
curl localhost:8000/api/health/ # {"status": "ok", "db": "ok"}
```

Migrations run automatically when `web` starts. To create an admin (role `admin`, and access to the Django admin at `/admin/`):

```bash
docker compose exec web python manage.py createsuperuser
```

To see the whole flow work end to end (register, book, review, summarise through the worker):

```bash
scripts/smoke_test.sh
```

Stop with `docker compose down` (add `-v` to delete the database).

## Try the API

```bash
API=localhost:8000/api

# register a provider and a customer (admins can't self-register)
curl -X POST $API/auth/register/ -H 'Content-Type: application/json' \
  -d '{"username":"prov1","email":"prov1@example.com","password":"S3cure-pass!","role":"provider"}'
curl -X POST $API/auth/register/ -H 'Content-Type: application/json' \
  -d '{"username":"cust1","email":"cust1@example.com","password":"S3cure-pass!"}'

# log in: returns {"access": ..., "refresh": ...}
curl -X POST $API/auth/token/ -H 'Content-Type: application/json' \
  -d '{"username":"prov1","password":"S3cure-pass!"}'

# use the access token on every other request
curl $API/slots/ -H "Authorization: Bearer <access token>"
```

## Endpoints

| Method | Path | Who | Notes |
|---|---|---|---|
| GET | `/api/health/` | public | DB check, used by healthchecks |
| POST | `/api/auth/register/` | public | role `provider` or `customer` |
| POST | `/api/auth/token/` | public | login; `/token/refresh/` for a new access token |
| GET | `/api/auth/me/` | any user | current user |
| GET | `/api/slots/` | any user | `?provider=<id>`, `?available=true`; cached in Redis |
| POST | `/api/slots/` | provider | always for themselves |
| DELETE | `/api/slots/{id}/` | provider | own slot, only if never booked |
| GET | `/api/bookings/` | any user | scoped: admin all, provider own slots, customer own; `?status=` |
| GET | `/api/bookings/{id}/` | any user | someone else's booking returns 404 |
| POST | `/api/bookings/` | customer | `{"slot": id}` |
| PATCH | `/api/bookings/{id}/` | any user | `{"status": ...}`, allowed transitions depend on role |
| DELETE | `/api/bookings/{id}/` | admin | |
| POST | `/api/bookings/{id}/review/` | customer | completed bookings only, one review each |
| POST | `/api/providers/{id}/summarise/` | admin, provider (self) | queues a job, returns 202 |
| GET | `/api/summaries/`, `/api/summaries/{id}/` | admin, provider (own) | poll until `status` is `done` |

Booking status transitions:

| Role | pending → | confirmed → |
|---|---|---|
| customer | cancelled | cancelled |
| provider, admin | confirmed, cancelled | completed, cancelled |

## How access control works

1. **`RBACMiddleware`** ([accounts/middleware.py](accounts/middleware.py)) runs on every `/api/` request: it authenticates the JWT (401 if missing or invalid) and checks the caller's role against a `(route, method) → roles` table (403).
2. **Row scoping** ([bookings/models.py](bookings/models.py), `Booking.objects.visible_to(user)`): every booking query goes through it, so a provider never sees another provider's bookings and a customer only sees their own. Anything outside it returns 404.

## How Redis is used

- **Queue**: `POST /summarise/` saves a `queued` summary row and enqueues `summarise_reviews(summary_id)` on the `default` RQ queue. The `worker` container runs it and writes the result to Postgres. The summary is a stub (count, average, common words) in place of an LLM call.
- **Cache**: the slot list, the most frequent read, is cached for 60s. Any slot or booking change sets a new cache version, so stale entries are never read. If Redis is down, requests fall back to Postgres.

## Tests

Tests run against real Postgres and Redis (a separate `test_` database and Redis DB 15, so dev data is untouched).

```bash
docker compose up -d                           # Postgres on 5433, Redis on 6380
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
set -a; source .env; set +a
pytest -v
ruff check . && ruff format --check .
```

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on every PR and push to `main`:

1. **Lint**: ruff.
2. **Tests**: pytest with Postgres and Redis service containers, plus a check for uncommitted migrations.
3. **Smoke test**: builds the real stack with Docker Compose and runs `scripts/smoke_test.sh` against it.
